KyRecovery / Backups & recovery

Backups sealed.
Recovery shared.

A home for encrypted backups that cannot open them. Your applications seal the data; your chosen custodians hold the shares needed to recover it.

Source available · Self-hosted
Read configuration guide ↗View source ↗

At a glance

Is it for you?

For operators of Ky applications who want a shared backup destination while keeping the ability to decrypt backups out of the storage server.

How you use it
Run the server behind HTTPS with persistent storage. Complete the recovery-key ceremony, distribute custodian cards, then pair compatible products.
Availability
Server source and operator documentation are available. Check each product’s current backup and restore instructions before connecting it.

Inside KyRecovery

Store the backup.
Separate the keys.

01

Sealed before upload

Products encrypt their own backup containers before sending them. KyRecovery stores those sealed bytes, without the recovery private key or any custodian share.

02

Recovery by agreement

Choose how many custodian cards are needed to recover the data. For example, a three-of-five arrangement requires any three of five shares to open a backup.

03

Copies beyond one server

Replicate sealed containers to configured S3-compatible storage, SFTP, SMB or a local directory. Review the documented transport limitations and verify your offsite copies.

From backup to recovery

Three distinct jobs.

Integrity is not a restore test.

KyRecovery can check that stored bytes still match their recorded digest. It cannot decrypt a container or prove that your application will restore successfully. Follow the product’s recovery runbook and test your recovery process.

For operators

Keep track of what you keep.

Pair with a short code

An administrator generates a time-limited, single-use pairing code. The product receives the public recovery key and a deposit-only token: it cannot use that token to browse or download backups.

Check stored copies

On-demand checks and a daily integrity sweep compare containers with their recorded SHA-256 digests. A hash-chained audit ledger records deposits, verifications and administrative events.

Control retention

Keep recent backups plus weekly and monthly copies. Review the expiry preview before manually purging. Offsite destinations need their own retention policies; a purge can remove a product’s last local backup.

Prepare before you need it

Recovery starts with people.

Run the ceremony

The recovery keypair is generated in the administrator’s browser. Print and distribute the custodian cards, then close the ceremony tab. Only the public key and threshold settings are sent to the server.

Protect the cards

Keep shares separately and choose a threshold your custodians can actually meet. If too few shares remain available, the server cannot unlock the backups for you. Recovery-key rotation is not yet implemented.

Look after the store

Back up the database, server secret key and capsule directory together. Plan storage capacity and monitor deposits. The server secret key protects its own credentials; it does not unlock the sealed backups.

Part of your Ky setup

KyIdentity can provide dashboard sign-in; local administrator login is also available. Backup schedules and restore commands belong to the connected products. During pairing, compare recovery-key fingerprints or pin the public key by hand, following the product’s instructions.

KyRecovery still holds account information, backup metadata and audit records. “Blind store” refers to encrypted backup contents, not an absence of operational data. Operators are responsible for access and retention. Read the Busnes.app privacy policy.
