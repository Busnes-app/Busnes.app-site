KyDrive for Android Documentation

KyDrive for Android

KyDrive is the Android client for your organization’s self-hosted KyDrive server. Use it to browse your personal files and shared workspaces, open files in another Android app, upload files, save copies to your phone, create folders, rename items and restore items from trash.

The server holds the files and decides who may access them. Your phone links to your account by scanning a short-lived QR code from the web app. You do not type your suite password into the Android app.

This manual follows the chapter-based mdBook format used by KyPost’s documentation. The chapter menu, search button and print button help you find a task or save a reading copy. Markdown sources are also readable directly on GitHub.

Start here

  • Everyday work: files and workspaces and uploads and downloads.
  • Protect or remove a link: app lock and unlinking.
  • Something went wrong: troubleshooting.

Current scope

The app is pre-release software. This book describes implemented behavior, rather than the full product roadmap. There are no published production releases or store listings offered by this repository yet.

Automatic photo backup, persistent offline copies, two-way folder synchronization, in-app document editing and a system DocumentsProvider are not available in this app. Opening a file uses another installed app. Receiving an existing share is supported; creating a new share or guest link uses the web app. The separate desktop client provides two-way folder sync.

The approved roadmap and owner decisions are in DESIGN.md. An item in that design document is not a claim that the feature has shipped.

Getting started

Requirements

RequirementWhat you need
Phone or tabletAndroid 12 (API 31) or newer
AccountAn active account on a KyDrive server with phone QR linking and device request signing
NetworkThe phone must reach the server’s HTTPS hostname; connect to the organization’s LAN or VPN if required
Server certificateA valid certificate for that hostname, chaining to an Android system CA
CameraNeeded to scan the link code; permit camera access when Android asks
File viewerAn installed app that can open the file type you choose

Google Play Services, Firebase, a push distributor and a separate KyAuth app are not required. KyDrive Android contains no analytics or crash-reporting SDK.

The app refuses cleartext HTTP, user-installed certificate authorities and redirects. An administrator must configure the final HTTPS origin directly. Installing a private CA on the phone does not make that CA acceptable to this app.

Install a development build

No production download is currently published. Developers can build and install a debug APK for testing; follow Development and testing. Use a test account and a disposable device or emulator when evaluating a development build. An unsigned release APK is a build check, not an installable published release.

When updating an existing development installation, use a build signed with the same key. Android rejects an update signed with a different key. Uninstalling to switch keys removes the app’s local session and requires linking again; copies saved outside KyDrive and files on the server remain separate.

First run

  1. Open KyDrive. An unlinked app shows Link this phone and Scan the code.
  2. Link the phone from a browser session on a second screen.
  3. Check the displayed account, then choose whether to set an app PIN when offered.
  4. Open Files for your personal workspace or Shared for shared workspaces and directly shared items.

Settings remains available before linking for appearance preferences and version information. Account and security controls appear after a phone is linked.

Link a phone

Linking authorizes this installation to access your account. Each phone has its own device token and signing key, so an administrator can revoke one phone independently.

Scan and confirm

  1. On another screen, sign in to the KyDrive web app using your ordinary account.
  2. Open Settings → Phones & apps → Link a phone and complete the server’s step-up check. The server may label its device-management section differently in older versions.
  3. On Android, tap Scan the code. Allow camera access and scan the QR code displayed by the server. The app scans QR codes; it does not accept a typed password or manual token.
  4. Read the server hostname in Link this phone?. Continue only if it is the server where you opened the link screen yourself, then tap Link.
  5. Wait for Linked as …. Open Settings to check the server and account.

The code is single-use and expires after two minutes. If it is already used or expired, show a fresh one and scan again. Do not send the QR code to someone else or attach it to a bug report: anyone who redeems it in time may link a device.

The app generates a non-exportable signing key before redeeming the code and verifies that the returned device token belongs to the account the server identified. It then stores the encrypted session on the phone. Scanning a code without confirming and successfully completing the exchange does not link a phone.

Linking again

If the app says This phone was signed out. Link it again, show a new code on the same server and for the same account. A signed-out installation retains its account binding. Linking it directly to a different account or server is refused; first use Unlink this phone.

If the server revokes the device, the app erases its local session when it next receives that result. It must then link again as a new device.

After linking

The app offers Lock KyDrive with a PIN?. Choose Choose a PIN to enable it, or Not now and configure it later under Settings → Security. See Settings and app lock for the consequences of each setting.

Files and workspaces

Navigate

Files opens My files, your private personal workspace. The server creates that workspace on first use if necessary. Shared lists organization workspaces you may access and files or folders shared directly with you.

Tap a workspace or folder to enter it. The Up button and Android Back move through the current tab’s folder history. Files and Shared keep separate histories during the current session. Workspaces and folders appear before files, sorted by name; file rows show their size and modification date when available.

Use More options → Refresh to reload the current listing. An empty personal folder says This folder is empty. An empty Shared list means there are no visible shared destinations for this account; ask the workspace owner about membership.

Permissions

LabelWhat Android exposes
Can viewBrowse, open and save permitted files
Can editView actions, uploads, new folders, rename, trash and restore
Can manageThe same file actions; permission management uses the web app

The server remains authoritative. A permission can change while a screen is open, and the server can refuse an action even when it was previously visible. A direct share does not grant access to the rest of its workspace. People and group membership are managed through the suite’s directory and web administration, not the Android app.

Open a file

Tap the file, or use its Actions → Open menu. Android starts a compatible installed viewer. KyDrive grants that viewer read access to a stream of the selected revision; it does not make a persistent offline copy. If the file changes on the server, the old stream cannot silently switch to the new revision.

If no viewer is installed, the app says No app on this phone opens this kind of file. Install a suitable viewer, or use Save to this phone. Changes made in another app are not automatically uploaded to KyDrive.

New folder and rename

  1. Open a writable workspace and the destination folder.
  2. For a new folder, choose Add → New folder. To rename an item, open the Actions button beside its name and choose Rename.
  3. Enter the name and tap OK. Cancel leaves the item unchanged.

Names must occupy 1–255 UTF-8 bytes, without slashes, backslashes, control/format characters or leading/trailing whitespace; . and .. are not accepted. Some non-English characters occupy several bytes. The server can also reject a conflicting name. Refresh the listing before retrying a conflict.

Trash and restore

Choose Actions → Move to trash to trash an item. The confirmation message offers Undo, which asks the server to restore it. To restore later:

  1. Open its workspace and choose More options → Trash.
  2. Find the item, open Actions, and choose Restore.
  3. Return to the live listing and refresh if needed.

Trash is a flat list for the workspace. Restore requires write permission. Android does not expose permanent deletion or trash-retention controls. Trashed content and retained versions may still count against the server’s storage quota.

Uploads and downloads

Upload files

  1. Open the writable workspace and folder where the files should go.
  2. Choose Add → Upload files.
  3. Select one or more files in Android’s file picker.
  4. Watch for Uploading …, followed by Uploaded … or an error.

The selected provider must expose a valid filename and a known size. If either is missing or unsupported, the app says Can’t upload …: its name or size is unknown or not allowed. Save the item as an ordinary file in a provider that supplies both, then select that copy.

Uploads run in the app process and may continue after you leave the screen. They are not scheduled work that is guaranteed to survive Android killing the process. The wire layer uses 8 MiB chunks and asks the server for the accepted offset after a failed chunk, with at most five failures for that chunk. There is no user-facing persistent transfer queue or restart/resume button yet. Refresh after an uncertain result before starting another upload.

Save a copy

  1. Open a file’s Actions menu and choose Save to this phone.
  2. In Android’s save picker, choose a destination and filename, then confirm.
  3. Wait for Saved … before relying on the copy.

The destination may be local storage or another document provider. The downloaded bytes must match the size and SHA-256 digest the server listed. A changed or damaged file fails with The file changed or arrived damaged, so nothing was kept. Try again. The app attempts to remove the incomplete destination; a provider that refuses removal may leave a partial file, which you should delete using that provider’s own controls.

Opening and saving are different

Open lets another app read a stream while KyDrive remains linked, unlocked and able to reach the server. It does not create an offline copy for you.

Save to this phone writes a separate copy to your chosen destination. That copy is outside KyDrive’s encrypted session storage and remains after unlinking or revocation. Protect and delete it using the destination app or Android’s file manager. Edits to a saved copy do not synchronize automatically; upload a file explicitly if you need it stored on the server.

Failed transfers

  • Not enough space: the workspace quota is full. Ask its manager about quota and retained content. Android cannot increase a quota or empty server trash permanently.
  • Permission denied: refresh and check your workspace access with its owner.
  • Changed on the server/name taken: refresh; do not assume a retry may overwrite someone else’s version.
  • Network lost or app stopped: reconnect, refresh and verify the server/destination before repeating the transfer.

See Troubleshooting for connection and account errors.

Settings and app lock

Open Settings from the main screen. Linked installations show the server, account and device name under Account, followed by the security options.

Appearance and navigation

Appearance → Mode offers System, Light and Dark. System follows Android; the other choices override it for this app. On a large screen, choose Left or Right for Navigation rail on large screens. The initial rail side is Right. These preferences are stored on this installation.

About shows the app version and licence information. Include the version and full source commit, if known, when reporting a development-build problem.

Enable a PIN

  1. Under Security, turn on Lock KyDrive with a PIN.
  2. Enter a new PIN of 8–12 digits, then enter it again.
  3. Complete setup while the app remains on screen. If it leaves the screen during setup or checking, the lock may require you to unlock again before showing files.

Very common PINs, repeated digits and simple ascending/descending runs are refused. Do not use your account password as the PIN. A PIN protects this app’s user interface; it is not your server password and cannot recover a server account.

Lock and erase settings

SettingChoicesInitial value
Lock after leaving the appAt once, 30 s, 5 min30 s
Erase KyDrive from this phone after wrong PINs10, 20, 30, Never30
Unlock with fingerprint or faceStrong biometric when supportedOff until enabled

The third wrong PIN introduces a 30-second delay. Later failed attempts increase the delay through one minute, five minutes, 15 minutes and 30 minutes to an hour. Failed attempts are persisted; restarting the app is not a way to gain fresh guesses.

Reaching the selected erase threshold removes the app’s local keys and session. Server files and separately saved copies remain. Never disables that automatic erase threshold; it does not disable the delays.

Turning the lock off, lengthening its grace period or increasing/disabling its erase threshold requires the current PIN. Change PIN asks for the current PIN first. Strengthening the settings does not require weakening the existing protection.

Biometric unlock

If Android supports a strong fingerprint or face authenticator, enable Unlock with fingerprint or face and confirm your PIN. The option may be absent when the device does not support a sufficiently strong authenticator.

Adding or changing biometric enrollment invalidates the app’s biometric key. Use the PIN, then authorize biometrics again. Biometric availability and screen-unlock settings are also controlled by Android.

If you forget the PIN

There is no PIN recovery or remote unlock. You can remove the app’s local data through Android settings or reinstall it and link again. That removes this installation’s session; revoke the old phone entry in the server’s device settings as well. Server files remain available through another authorized session.

Locking also stops further file reads through KyDrive’s open-file stream. It cannot recall bytes that another app already read. Background transfers may continue while the screen is locked; see Privacy and security.

Sign-out, revocation and unlinking

These actions have different effects. Copies you saved outside KyDrive are not part of the app’s local session and are not removed by any of them.

EventWhat the phone doesWhat remains on the server
Ordinary invalid/expired tokenShows signed out and asks to link again; retains the account bindingServer files and the server’s device record
Server revokes this deviceErases local keys and session when the next request receives device_revokedServer files; server manages the revoked record
Unlink this phoneTries to revoke the device, then erases local keys/session even when unreachableServer files; remove a stale device record manually if the request failed
Wrong-PIN erase threshold reachedErases the app’s local keys/sessionServer files; manage the old device record in the web app

Link again after sign-out

Generate a fresh code for the same account and server, then link again. The app refuses a replacement link to another account or origin until you unlink.

Unlink from the phone

  1. Open Settings → Account → Unlink this phone.
  2. Read the confirmation naming the server, then choose Unlink this phone.
  3. The app attempts revocation and wipes its local session regardless of the result.
  4. If it says the server could not be reached, remove that phone under Settings → Phones & apps in the web app too.

Unlinking deletes keys before removing the stored session, making encrypted session data unreadable. An interrupted wipe is retried when the app next loads its session. It does not delete your server workspace or files you saved through Android’s picker.

Revoke a lost phone

Use an authorized browser session to revoke the phone in the server’s device settings. Future server requests using that credential are refused. A phone that is offline cannot receive the revocation until it contacts the server; revocation is not a remote guarantee that every previously delivered byte has vanished.

Also use Android’s own lost-device controls as appropriate. Protect separately saved copies and copies already delivered to other apps using their own controls.

Troubleshooting

Linking and connection errors

Message or symptomWhat to check
That is not a KyDrive link codeScan the server’s phone-link QR code, not a browser sign-in, desktop link or file-share QR code
Code was already used or expiredGenerate a fresh code and scan within two minutes
Phone holds another account’s filesUnlink in Settings before switching account or server
Could not reach the serverCheck Wi-Fi/mobile data, LAN/VPN requirements, DNS and the exact HTTPS hostname
Phone does not trust the certificateAsk the operator to check validity dates, hostname and complete certificate chain to Android system CAs; the app also enforces its certificate-strength policy
Server refused to link this phoneCheck server compatibility and its device quota; provide the error number to the operator
Camera cannot scanGrant camera permission in Android settings, improve lighting and show a fresh unobstructed code

The app has no “ignore certificate errors” switch. User-installed CAs are intentionally not trusted. Fix the server certificate or use an appropriately trusted HTTPS endpoint. Android’s clock must be accurate for both certificate validity and signed-request time checks. Older servers may require an upgrade to support phone linking and device signing.

Files and workspace access

Message or symptomNext step
Shared is emptyAsk the workspace owner to verify your group membership or direct share
You don’t have permissionRefresh; ask the owner about current access
That is no longer thereRefresh; the item may have moved, been trashed or become inaccessible
Changed on the server/name takenRefresh and use a different name where appropriate
Not enough spaceAsk the workspace manager about quota, trash and retained versions
No app opens this kind of fileInstall a compatible viewer, or save a copy using the file’s Actions menu
Can’t upload: name/size unknownChoose a normal file whose document provider exposes a valid name and size
File changed or arrived damagedRefresh the listing and retry; remove any partial destination if its provider refused cleanup

Write controls depend on the current workspace and role. They are absent in read-only destinations and trash, and the server independently checks every request.

Lock problems

For Too many wrong PINs, wait for the displayed delay. Restarting the app does not clear failed attempts. If biometrics stopped after enrollment changed, unlock with the PIN and enable biometrics again. If you forgot the PIN, see If you forget the PIN.

A blank recent-app card or blocked screenshot is intentional screen protection in production builds. It is not a rendering failure.

Report a bug

Use GitHub Issues for ordinary bugs. Include the app version/source commit, Android version and device type, the server version, reproduction steps, expected result, actual result and displayed error number. Say whether it happens on Wi-Fi, mobile data or a VPN.

Do not include device tokens, PINs, QR codes, private filenames or file contents. Report suspected vulnerabilities privately through SECURITY.md.

Privacy and security

The authoritative reporting process and maintainer commitments are in SECURITY.md. This chapter explains what a person using the app can rely on and where protection ends.

Data on the phone

The device token and linked account record are stored in the app’s private noBackupFilesDir, encrypted with a non-exportable Android Keystore AES-256-GCM key. The per-link P-256 request-signing key also stays in Keystore. Display preferences and the salted, iterated PIN verifier are separate from that token; the verifier is mixed with a Keystore HMAC key. Raw PINs are not saved.

The current app streams opened files instead of maintaining a persistent offline file cache. Save to this phone deliberately creates a copy at the destination you choose. That destination and any external viewer have their own storage and confidentiality rules. KyDrive cannot revoke or erase copies they already received.

Android backup and device-transfer extraction are disabled. There is no Android-session export or restore feature. If the installation or its Keystore keys are lost, link again; authoritative files remain on the server. Server disaster recovery is the server operator’s responsibility, not a backup performed by this Android client.

Network trust

The app uses HTTPS to the confirmed server origin, with Android’s system CAs and normal hostname verification. It refuses redirects and cleartext traffic. The certificate strength policy adds checks during the TLS handshake: RSA keys of at least 2048 bits, elliptic-curve keys of at least 256 bits, and SHA-2 or stronger verified certificate signatures across the validated chain. The self-signature of a trust anchor is not used as a security proof; the anchor’s key strength is still checked.

The current policy accepts measurable RSA and EC certificate keys and named SHA-2 signature algorithms. Ed25519 keys and RSASSA-PSS certificate signatures are currently refused because this policy does not measure them; that refusal is not a claim that those algorithms are weak. Operators need a certificate chain the policy supports.

Each linked-device request is signed using its non-exportable P-256 key and SHA-256. The signed request format binds origin, method, target, timestamp, nonce, selected state-changing headers and body digest. The server enforces device permissions and replay checks. These signatures supplement HTTPS; they do not hide file contents from the server or from a TLS endpoint the phone trusts.

Dedicated developer screenshot/test builds can trust a throwaway CA through Android’s debug-only configuration. This does not enable user CAs or certificate bypass in a production build.

Screens and app lock

Production screens use Android’s secure-window and overlay protection. Text fields ask keyboards not to learn from entered text. An installed keyboard and Android remain part of the trusted device environment; these requests are not a defense against a compromised OS or malicious root-level software.

The optional PIN/strong-biometric lock gates the screen and further reads through KyDrive’s shared-file stream. It does not require user authentication for the device token/signing key because in-process background transfers must continue while locked. Set a secure Android screen lock as well as the app lock.

Collection and limits

The app has no analytics, crash SDK, advertisements or Google Play Services requirement. It sends API requests and selected uploads to your configured KyDrive server. The server and its operators can read its stored files: this is not end-to-end encryption.

The app cannot protect against a compromised server, root-level phone compromise, bytes retained by another app, or copies you saved outside it. No independent security audit is claimed. Review this chapter before relying on the pre-release app for sensitive work.

Architecture and API reference

This chapter is for developers integrating or changing the Android client. The KyDrive server source defines the API; the Android app does not define a separate wire protocol.

Linking input and output

The QR payload is kydrive://link?srv=<encoded-origin>&code=<code>. srv must be a bare HTTPS origin with a hostname, optional port, no user information, query or fragment. code is exactly 43 base64url characters. Duplicate/unknown parameters, malformed escapes and unsupported origins are refused before a network request.

POST /api/devices/token sends form fields grant=qr, code, name, platform=android and publicKey (standard-base64 SPKI DER). The response supplies a kyd_ token, user_id and user. GET /api/drive/device must identify the same account before the session is saved. DELETE /api/devices/self revokes the current phone.

Never log or place the device token in a URL. The app sends it as Authorization: Bearer …; request signatures are separate headers. The signature golden vector in app/src/test/resources/device-signing-v1.json is shared with the server.

Names from the server are display values, not local paths. API JSON responses are bounded; malformed JSON becomes an I/O failure. Non-success replies expose a status, structured error code and optional wipe field internally. Raw server error text is not displayed verbatim to users.

401 with device_revoked wipes regardless of its wipe boolean. Ordinary 401 marks the account signed out. Other status codes map to the messages in Troubleshooting.

Change the wire contract

Read the server’s current API and both repositories’ AGENTS.md files before changing a request. Put server changes in a separate server PR. Update the shared signature vector and interoperability tests when its format changes. Bump the real-server CI pin when a client needs newer routes; a local test against a different server is not evidence that the pinned CI integration ran.

Development and testing

Read the root contributor guide and the AGENTS.md chain for paths you will change. The repository uses Gradle’s Android application plugin and a version catalog; use its committed wrapper, not a globally installed Gradle.

Toolchain

  • JDK 25 for the Gradle daemon and the Android SDK with API 36.1.
  • ANDROID_HOME pointing to that SDK; platform-tools for adb.
  • An API 36 disposable emulator for device regressions, with hardware acceleration.
  • A built KyDrive server for integration tests; CI builds a pinned public commit.
  • mdBook 0.5.4 and Python 3 to build and check this manual.

Agent Android builds and emulator work run on the Major build host, each in a memory-capped systemd-run scope. Reuse the toolchain’s normal caches. Do not run Gradle on the owner’s workstation or switch test instances onto production push relays. Set PUSH_RELAY_URL= and APNS_RELAY_URL= for throwaway instances.

Build and install

From the repository root on the build host:

./gradlew assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk

The application ID is org.kysecurity.drive. Android displays the name KyDrive. The debug APK uses the build host’s debug signing key. A production release signing and distribution process has not been published; assembleRelease currently builds an unsigned APK to exercise R8 and resource shrinking.

Required checks

./gradlew testDebugUnitTest lintDebug checkExportedComponentsDebug checkExportedComponentsRelease assembleRelease
git diff --exit-code -- gradle/verification-metadata.xml
scripts/check-no-binaries.sh
mdbook build docs
python3 scripts/check-docs.py

Record commands, results and skips in the PR. A plain JVM run skips RealServerTest unless the server binary is supplied; it does not establish integration success.

Real server

KYDRIVE_SERVER_BIN=/absolute/path/to/kydrive-server ./gradlew testDebugUnitTest --tests '*RealServerTest'

Use a binary matching the commit pinned in .github/workflows/ci.yml when reproducing CI. That job fails if the integration report contains skipped or zero tests.

Fuzzing

JAZZER_FUZZ=1 ./gradlew testDebugUnitTest --tests 'org.kysecurity.drive.core.LinkUriFuzzTest'

The fuzz run is bounded by maxDuration in the test. Ordinary unit runs replay the committed seeds. Preserve a fixed finding as a regression input instead of claiming that one clean fuzz run proves the parser has no bugs.

Device tests

./gradlew connectedDebugAndroidTest

Use a disposable emulator. LockRecreationTest checks lock gating across Activity recreation. Certificate-floor device tests require a dedicated debug build trusting their throwaway CA; their exact invocation and no-skip report checks are in .github/workflows/ci.yml. Regular builds trust only system CAs. Test keys/certificates must never enter a production APK.

The fixture CA’s private key is public in the repository. An APK explicitly built to trust it is for isolated synthetic tests only; never link a real account with that APK.

Dependency verification

Gradle verifies artifact SHA-256 values from gradle/verification-metadata.xml, and CI fails if that file changes unexpectedly. Dependency updates require their own reviewed metadata regeneration commit. Follow the clean-home procedure in AGENTS.md; do not disable verification or add metadata writes to ordinary CI.

Screenshots

scripts/screenshots.sh creates phone/tablet captures in light/dark mode. A debug-only allowScreenshots property permits those captures. With KYDRIVE_SERVER_BIN set, the script starts a seeded throwaway server and trusts its generated CA through -PscreenshotCa. Ordinary and release builds retain secure windows and system-CA trust.

Changed screens need matching light/dark phone/tablet captures in the PR. A source-only TLS change does not require inventing a new screen for documentation.

Build the documentation

mdbook build docs
python3 scripts/check-docs.py

Open docs/book/index.html from the build output. Navigation, search and the print view are generated by mdBook. The documentation-book CI artifact contains the same static book for review; it does not publish a production documentation site.

Versions and releases

KyDrive Android has no published user release yet. Its current development version is 0.1.0, with Android versionCode 1. Identify a development build by its full Git commit ID as well as its display version; a version name alone does not distinguish unreleased snapshots.

The human-written changelog records the changes in the current development series. It describes browsing, transfers, linking, locking and security/verification changes, with explicit limits. The Android Settings → About screen shows the display version.

Release requirements

Before publishing a user release:

  1. Obtain the owner’s release authorization. Agent badge or documentation work does not authorize a tag, release or store submission.
  2. Assign a unique version name, increase Android’s version code, and record the exact source commit. Keep release identifiers retrievable from version control.
  3. Promote the changelog into dated human-readable release notes. Explain meaningful behavior and upgrade effects, including account relinking or server compatibility.
  4. Identify each fixed publicly known project vulnerability that already has a CVE or equivalent advisory identifier. Do not silently describe a security fix as routine cleanup.
  5. Pass full build/test/lint/exported-component checks, integration/device tests, static and dynamic analysis, and resolve confirmed security findings before release.
  6. Verify production configuration excludes test CAs, fixture keys and screenshot exceptions; use an owner-approved signing/distribution process.

Installing an APK signed with another key is not an ordinary update. Document channel or signing-key migrations before release, including whether uninstall/relink is needed and what local data is removed.

The Best Practices form reports project practice status, not release readiness or an independent security audit. Read the live form for its current status rather than assuming every source snapshot has earned or retained a badge.

Contributing

Read CONTRIBUTING.md for setup, security requirements and the pull-request process. The suite contribution policy also applies. Major functionality includes automated tests; warnings are fixed or documented as false positives.

Report ordinary bugs and proposed enhancements in Issues. Include reproducible steps and environment details. Discuss a major feature before implementation so its scope and server/API dependencies can be assessed. Documentation, small fixes and test improvements can be proposed directly.

Send vulnerabilities privately using SECURITY.md. Public bug reports are not the place to publish a working credential or exploit against someone’s deployment.

Keep this book current

Edit Markdown under docs/src/; register new chapters in SUMMARY.md. Keep current UI labels and implemented workflows aligned with source. Put plans in docs/DESIGN.md and clearly distinguish them from instructions for available features.

Build with mdBook and run the generated-link checker before submitting. Commit the sources and configuration; generated docs/book/ is a review artifact. Screenshots must come from disposable test systems and must not contain real account data.
