Busnes.app / Security

Security, plainly

What each Ky app protects, what your server can still see, and what has not been proven yet. Last updated October 20, 2026.

The short version

Built carefully. Not yet audited.

This page summarises each app's own security documentation. Where they differ, the repository is the source of truth, and the difference is a bug worth reporting.

No independent audit
No Ky app has had an independent security audit yet. Every app has automated tests, and most run Go vulnerability scanning, CodeQL or OpenSSF Scorecard in CI, but that is not the same as an outside review.
You run the server
Whoever controls the host, its data volume or the Docker socket controls the app. Most apps keep their encryption key on the same volume as their database, so a copy of that volume can be decrypted. The servers speak plain HTTP; HTTPS comes from the reverse proxy you put in front.
The server ships the web app
Web clients, including the end-to-end encrypted ones, run JavaScript your server sends. A compromised server could send code that leaks what you type. End-to-end encryption protects stored data and backups, not a server that has been taken over.
Backups the apps can't read
Each app seals its backup to a recovery key that only k of n custodians can open together. KyRecovery stores the sealed files plus a small unencrypted label (app, version, size, hash). KyRecovery, KyIdentity, KyNotes and KyDNS each carry a test that fails if server code outside the offline restore command gains a way to decrypt.
What we run
Push relays for the published phone apps (Cloudflare Workers that pass a notification to Google or Apple) and this website. The privacy policy lists what the relays receive and keep.
Found a problem?
Use "Report a vulnerability" on the repository's Security tab, or email hello@busnes.app with "Security" in the subject. How reports are handled.

KyIdentity and KyAuth

Protects. Passwords are hashed with Argon2id, and ten failed attempts lock an account for 15 minutes. Second factors are passkeys, authenticator codes, recovery codes and push approval where you type the two-digit number from the sign-in screen into KyAuth, limited to five pushes per user per hour. Sessions are server-side, and only a hash of each session token is stored. TOTP secrets, connector credentials and mail settings are encrypted at rest with AES-256-GCM. Calls to connected apps and to phones' push services go through one guarded client: HTTPS only, no redirects, private addresses refused by default. The push relay and Google's attestation list are fixed HTTPS addresses.

KyAuth, the phone app, keeps authenticator secrets in an encrypted vault unlocked by biometrics or screen lock, and signs approvals with a key held in secure hardware (the Android Keystore or the iPhone Secure Enclave). On Linux phones the vault is encrypted with your passcode, and there is no hardware keystore. Secrets never leave the phone, and the app has no backup or sync, so a lost phone means re-enrolling.

Your server can see usernames, email addresses, groups, app assignments and the audit log with client IP addresses, all unencrypted. Anyone with the data volume has the encryption key too.

Talks to. If your operator sets up our push relay, sign-in requests to Android (Firebase) and iPhone go through it to Google or Apple. iPhone pushes are encrypted to keys on the phone, for pairings made with a current version of KyAuth; iPhones paired before October 13, 2026 should pair again. Android pushes through Firebase are not encrypted: the relay and Google see the request's opaque IDs, but not your username. UnifiedPush and Ubuntu Touch pushes are encrypted and skip our relay entirely. By default the server also fetches Google's Android attestation status list.

Doesn't protect against a compromised host, or a misconfigured trusted-proxy setting, which lets callers fake their IP address and slip past rate limits. Apps that don't support back-channel logout keep their own sessions after you sign out of KyIdentity.

Still unproven. Device attestation and encrypted iPhone pushes have not yet been confirmed on real hardware, and KyAuth for iPhone has no published release. Before a recent fix, push approval could be bypassed; that is now covered by regression tests.

KyPost

Protects. Your PGP private key is created or imported and wrapped in your browser, and the server receives only the wrapped copy. The browser splits your password so the server never sees the half that unlocks your key. Each device you set up for encrypted mail gets its own sealed copy of the key: in the Android Keystore, or the Secure Enclave on iPhone and Mac. KyPost for Linux imports the key into your GnuPG keyring. IMAP passwords and TOTP secrets are encrypted at rest. Sign-in supports authenticator codes, push approval, OpenID Connect and a local proof-of-work CAPTCHA.

Your server can see all ordinary mail, since it reads it to label it, plus the routing details and labels of PGP mail. Contacts, rules and history are not encrypted. Anyone with the private key folder can decrypt the stored IMAP passwords and TOTP secrets.

Talks to your mail provider, which can see a PGP message's subject unless the sender hid it, as KyPost does. The AI labelling model runs inside the container, and a test proves PGP mail is never sent to it. If you point it at another host, that host sees your ordinary mail. Android and iPhone notifications pass through our relay and Google or Apple, unencrypted. By default they carry no sender or subject, and PGP mail never shows a preview. UnifiedPush, App Pull and KyPost for Linux skip our relay.

Doesn't protect against a compromised server serving malicious browser code, or prompt injection steering the labels. Labels are a convenience, not a security boundary.

Still unproven. Receiving mail directly into KyPost is opt-in and still being qualified. The iPhone and Mac apps have no published release, and Android releases on GitHub are still drafts.

KyRecovery

Protects. Each app seals its own backup with hybrid post-quantum encryption (X-Wing: ML-KEM-768 with X25519, then AES-256-GCM) before upload. The recovery key is generated in the operator's browser and split into k-of-n custodian cards, and only the public key reaches the server. A test in CI, TestNothingInTheServerDecrypts, fails if any server code imports what it would need to decrypt.

Your server can see each backup's size, hash and unencrypted label (app, version, key ID), plus custodian names, app tokens and the audit log. It cannot see backup contents.

Talks to the off-site targets you configure: S3 or R2 over HTTPS, SFTP with a pinned host key, SMB, or a local mount. Each receives only the sealed files.

Doesn't protect against an SMB server that grants an unsigned guest session. An impostor share could accept uploads that never land, so prefer S3 or SFTP. Restoring an old but valid backup is possible; check its date against the deposit record.

Key rotation. You can rotate the recovery key with a new ceremony and new cards. Old backups still open only with the old cards, because the server cannot re-seal what it cannot read. Each app picks up the new key only when you re-pair it and confirm the key ID printed on the new cards; until the Ky apps ship that support, re-pairing to a new key is refused.

Still unproven. The server records deposits but never claims a restore was verified, so test a restore yourself.

KyNotes

Protects. Notes are encrypted in the browser with a key per notebook (AES-256-GCM). Notebook keys are shared with teammates by wrapping them to each person's X25519 key. The server receives only a verifier derived from your password, never the password itself, and keeps a recovery copy sealed under a 128-bit recovery code it never sees. Tests check that a known plaintext marker never appears in logs, HTTP responses, database columns, blob storage or backups.

Your server can see who shares which notebook, object sizes, versions and times, and reminder times if reminder push is on. It cannot see note contents or keys.

Doesn't protect against a compromised server serving malicious browser code. An admin who resets a local account's password can also act as that user until the user changes it. Removed members keep whatever they already downloaded. Identical attachments are visibly identical.

KyDNS

Protects. The admin login uses Argon2id and hardened cookies. The admin UI answers only to allowed hostnames, which blocks DNS rebinding, and refuses cross-site writes. Only networks you allow can query it; allowing a public range has to be retyped and leaves a permanent warning. The container runs as a non-root user with every capability dropped. Replication between nodes uses TLS 1.3 with pinned certificates.

Your server can see your records and DHCP leases. Query logging is off by default, and logging client addresses is a separate opt-in.

Talks to upstream resolvers over DNS-over-TLS, by default Cloudflare (1.1.1.1) and Quad9. They see the names you look up, not which device asked. Blocklists are fetched over HTTPS only.

Doesn't protect against forged answers from upstream: KyDNS is not a validating DNSSEC resolver. Blocking is domain filtering, not malware protection. Write access to its database file equals admin access.

KyCalendar

Protects. Sign-in is local accounts with authenticator codes, or one OpenID Connect provider such as KyIdentity. Sessions and app passwords are stored only as hashes. TOTP secrets, feed links and connector secrets are encrypted at rest. In production it refuses to start without an https address unless you explicitly allow plain HTTP.

Your server can see every event. Calendar data is stored as plaintext. Inside the app, administrators get no access to anyone's calendars.

AI agents connect over MCP with tokens you create and can revoke at any time. Each token has one scope: read, edit only events it created, or edit any. Tokens reach personal calendars only, can't delete anything, can't add or change who is invited, never work over CalDAV, and are revoked after 90 days unused. The agent and its model provider see the events it reads, and event text can carry prompt injection the server cannot stop.

Still unproven. Server-side scheduling is unfinished and behind a flag. With PostgreSQL, KyCalendar makes no sealed backups; your own database dump holds every event in plain text.

KyDrive

Protects. Sign-in is through KyIdentity. Every file version is encrypted at rest with AES-256-GCM under its own derived key, and file names, thumbnails and extracted text are encrypted too. App passwords, agent tokens and share links are stored as hashes. Content search keeps an index of keyed hashes of words, never the words themselves, and shows only matches and snippets from files you, or an AI agent you connect, can read at that moment; guest links have no search. The desktop app keeps its token in the operating system's keyring.

Your server can see every file. This is not end-to-end encryption: whoever holds the deployment key can read everything, and that key sits beside the data unless you move it into a secret. Someone with the disk but not the key can still tell from the search index which files share words and how often words occur.

Talks to the self-hosted document editor, which processes files in plaintext; your Restic backup target, which receives encrypted data only; and any AI agent you connect, with a token that never exceeds your role, can't delete permanently, and expires after 90 days unused.

Still unproven. AI agent access, document text extraction and content search are in current source, not yet in the v0.4.2 release. Searching PDFs has not been tested against a real Euro-Office, and indexing has not been measured on a small NAS. The desktop app has no published release, so build it from source; the Windows build is unsigned and the macOS build is only ad-hoc signed.

KyMessages

Protects. KyMessages runs unmodified Synapse, Matrix Authentication Service, Element and LiveKit, pinned by image digest. Members sign in through KyIdentity only, with no password login, open registration or guest access. New rooms are encrypted end to end in Element, and a CI test checks that message text never reaches the database.

Your server can see room names and topics, membership, display names, times, devices and IP addresses. Synapse does not enforce encryption, so a client that doesn't encrypt can post readable messages into an encrypted room.

Talks to nobody by default: federation is closed. Servers you allow keep copies you can't recall, and a room on a public server reaches every server in it, allowed or not. Element's integrations, widgets and telemetry are switched off.

Still unproven. Encryption for calls, and encryption across federated servers, have not been verified.

KyYard

Protects. Sign-in uses Argon2id, authenticator codes and optional KyIdentity. Registry credentials are encrypted and write-only through the API. Remote agents join with a single-use token, then need a person to approve their fingerprint.

Your server can do a lot. Mounting the Docker socket gives KyYard root on that host, and it is not a sandbox. On Kubernetes it reads workload specs, events and logs cluster-wide, never Secrets, and writes only in the namespaces you list. Organisation admins can read containers' environment variables. AI agents over MCP are read-only by default. An admin can let one restart containers and apply update plans, but no agent can stop, delete, run commands or read secrets, and container logs can steer an agent.

Still unproven. The threat model is still a draft for review.

kyPulse

Protects. Sign-in uses Argon2id, authenticator codes and optional OpenID Connect. Webhooks, tokens and TOTP secrets are encrypted at rest, and the audit log is a keyed hash chain you can verify. Outbound checks refuse loopback, link-local and cloud metadata addresses. The container is read-only, non-root and published on loopback only by default.

Your server can see the health data and, for admins only, the logs it collects. It is read-only towards the apps it watches. The optional log shipper reads the Docker socket, which is root-equivalent, so put a read-only socket proxy in front of it.

Talks to your alert channels (ntfy, Gotify, Discord or a webhook). They receive the app name, its state and a link, never log lines, usernames or IP addresses.

KyQuickStart and KyQuickStart AI

KyQuickStart pins SSH host keys and generates each app's secrets on the target (owner-only files on Docker hosts, a locked-down pod on Kubernetes), and they never appear in command lines or its saved state. Its SSH user needs Docker access, which is effectively root on that host. It is pre-release, and its macOS build is unsigned.

KyQuickStart AI gives your AI agent a dedicated kyops login on each server: key-only, no password, no sudo, but in the Docker group, which is root-equivalent. Host keys are pinned, and revoke removes access afterwards. On your own computer the agent runs as you, and the limits in its prompt are instructions, not a barrier. Everything the agent reads or prints goes to your AI vendor. Secrets are meant to stay on the servers, but a misbehaving agent could read them. The login sheet is written owner-only to your computer, and you should shred it once your passwords are stored. It is a first test: use it on servers you can rebuild.

Reporting a vulnerability

Report privately with Report a vulnerability on the affected repository's Security tab on GitHub, or email hello@busnes.app with "Security" in the subject. Please don't open a public issue.

You'll get an acknowledgement within 2 business days. The target is public disclosure within 30 days for critical issues, 60 for high and 90 for moderate. A fix ships before the advisory, and reporters are credited unless they'd rather not be. Ky is maintained by one person, so a clear reproduction helps most.

Each repository's own SECURITY.md, where it has one, holds the full threat model and takes precedence over this summary.
